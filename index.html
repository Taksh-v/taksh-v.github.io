Why it exists

What's actually real

Assest — agentic company brain

Fragmented company knowledge — Notion, Slack, Drive, uploads — turned into one queryable, version-aware interface.

Status
In development · incubated prototype
Role
Founder · architecture · build
Stack
FastAPI backend + Next.js app · Postgres · Qdrant · graph
Stage
Incubated prototype moving toward design partners
Metrics
24,845 lines source · 7,996 lines tests · 167 test functions

Why it exists

Retrieval usually forgets that organisations change. A policy superseded last quarter shouldn't be answering today's question — and the people who wrote it shouldn't have to re-explain it every week.

What's actually real

  • Rerunnable ingestion with PII scrubbing and adaptive chunking
  • Hybrid dense + sparse retrieval fused with reciprocal rank fusion, unit-tested
  • Multi-vector semantic cache for repeat questions
  • ACL gates that run before search, not after
  • Connector workers with a dead-letter queue, so failures park instead of vanishing

What it demonstrates

Systems thinking at scale — near 25,000 lines of source with 8,000 lines of tests beside it, diagnostic scripts, and a repository you can actually navigate.

What I'd do differently

Schema-first, from day one. Migration debt ate days I didn't have — and I'd have shipped the guest demo before the internal polish, because a login wall is not a demo.

  • fusion + security tests
  • query pipeline

Qual — evaluation-first RAG

A market-intelligence pipeline that scores its own answers before it lets you trust them.

Status
Shipped · open source
Role
Design · build · evaluation
Retrieval
FAISS · hybrid lexical + vector (Qdrant migration outstanding)
Data
Live market feeds + RSS ingestion
Metrics
7,779 lines source · 4 evaluation metrics · 20 intelligence modules

Why it exists

I kept seeing impressive RAG demos with no way to know whether the answers were grounded. So the measuring stick came first: define quality, then build toward it.

What's actually real

  • A four-metric rubric: groundedness, completeness, relevancy, numeric-hallucination risk
  • Answers must cite sources; unsupported claims score lower
  • Quality gates and data audits before anything is indexed
  • Query rewriting, question classification and model routing
  • A macro layer with regime detection, sector mapping and cross-asset analysis

What it demonstrates

The instinct most junior engineers are missing: measurement as an engineering discipline rather than a retrospective slide.

What I'd do differently

Publish the evaluation report from the first run. The harness existed before the number did — and the number is the thing people actually want to see.

Evidence

  • Repository
  • run_rag_eval.py — the harness
  • data_quality.py — the gates

DDAS — duplicate detection in C

Duplicate detection across deeply nested storage trees, written against the raw file API.

Status
Rebuilding · not finished, labelled honestly
Language
C — no runtime, no garbage collector
Method
Custom hashing and a dedup index
Extras
Watch mode that catches files still being downloaded
Metrics
~3,200 lines of C across 8 iterations

Why it exists

To find out what my Python habits were hiding. File descriptors, buffers and hash collisions — the layer that stays invisible until it breaks.

What's actually real

  • ~3,200 lines of C walking arbitrarily deep directory trees
  • A hash index built for deduplication rather than shelling out to a diff tool
  • Explicit descriptor and buffer management over long I/O loops
  • A watch mode that spots a file arriving and points at the existing copy

What it demonstrates

Range. Most AI portfolios can't show a single line of systems code — this is where the fundamentals live.

Honest note

It currently looks like eight experiments (1.c … new4_DDAS.c) with no build file, no tests and no benchmarks. "Rebuilding" is the accurate label — one file and a benchmark table are the next commit.

Record

Where this started

DDAS came first — a duplicate-file detector I wrote for a hackathon, then kept rebuilding until detection got faster and it ran on any machine, not just mine. Before AI I was on Linux: shell, Kali's toolset, taking things apart to see how they worked. Harvard/edX CS50 came in 2025 out of pure curiosity — I simply wanted to learn Python properly.

Reading about ChatGPT pointed that instinct somewhere larger: if a script can automate a chore, can a system read market data and predict something? I spent the next year building RAG systems and fine-tuning models. Then I wanted to know what was actually happening underneath, so I took a Microsoft AI/ML bootcamp and learned neural networks and transformer architecture properly instead of treating the models as a black box. The market question never went away — it is why there is an evaluation-first pipeline on this board, and why my day job is strategy research inside a broking firm.

Assest pulled the rest together. While building an agentic company brain I worked through Y Combinator's startup programmes on my own — Startup School, the Request for Startups, how the batches actually work — and the idea that gave Assest its whole shape came from Garry Tan's company-brain concept. Credit where it is due; the building is the part that is mine, and it is open on GitHub.

That reading left me with one conviction: what makes a system authentic is proof of work and visibility. Most teams do the opposite — they keep everything under the hood until launch, waiting for a perfect product. I think that is backwards.

So this page publishes the work as it actually is. DDAS, the first thing I ever built, is the one currently marked Rebuilding. Every claim links to the code or the live thing. A résumé lists what I have done — it cannot hold why any of it exists, or the part that turns an idea into a product with customers on the other side of it. That is what this tab is for.
